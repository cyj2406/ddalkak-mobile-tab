# 남은 이슈 기록

확인하지 못했거나 이번 작업 범위 밖이라 고치지 않은 항목. 고치거나 확인하면 해당 항목에 결과와 날짜를 적는다.

## 1. 데스크톱 테스트 중 404 — `GET /favicon.ico` (2026-10-16 기록)

- **현상**: 요청 작성 입력 테스트(Playwright, 1280×900) 콘솔에 `Failed to load resource: the server responded with a status of 404 (Not Found)` 1회.
- **재현해서 확인한 정보**
  - 요청: `GET http://localhost:5173/favicon.ico` → 404. `curl`로도 404.
  - 시점: 새 브라우저 컨텍스트에서 **첫 페이지 로드 직후**(입력 조작 전, 테스트 단계 표시 `load`). 브라우저가 파비콘을 자동으로 찾는 요청이다.
  - 데스크톱에서만 보인 이유: 같은 스크립트에서 데스크톱 컨텍스트가 먼저 열렸고, 모바일 에뮬레이션 컨텍스트에서는 파비콘 요청이 기록되지 않았다.
  - 세 번 반복해 세 번 모두 같은 요청 하나뿐 — 입력 칸·InputField 변경과는 관계없다.
- **원인**: `index.html`에 `<link rel="icon">`이 없고 `public/` 폴더(파비콘 파일)도 없다.
- **처리 안 함**: 이번 범위(입력 넘침 규칙) 밖. 고치려면 파비콘 파일을 `public/`에 두고 `index.html`에 `<link rel="icon" href="/favicon.svg">` 식으로 연결한다(배포 사이트에서도 같은 404가 날 가능성이 높다 — 미확인).

### 같은 테스트에서 함께 보인 요청 실패

- `https://fonts.googleapis.com/css2?family=Pretendard+Variable:wght@400;500;600;700&display=swap` → **400**(`curl` 확인).
  `src/styles/fonts.css` 1행의 `@import`. Pretendard는 Google Fonts에 없는 글꼴이라 이 요청은 항상 실패한다.
  화면 글꼴은 바로 아래 3행의 jsDelivr `pretendardvariable-dynamic-subset.min.css`로 정상 로드돼(`docs/design-system.md` "Pretendard 800/900 확인 결과") 보이는 문제는 없지만,
  1행은 불필요한 실패 요청이다. 이번엔 고치지 않았다(1행 삭제로 해결될 것으로 보이나 미확인).

## 2. 모바일 키보드 — 실기기 미검증 (2026-10-16)

- `InputField`는 포커스한 칸이 커지거나 `window.visualViewport`가 줄면, 칸 아래 끝이 보이는 영역 안에 들도록 가장 가까운 스크롤 영역을 올린다.
- **확인한 것은 흉내뿐**: Playwright에서 375×667 → 375×360으로 **화면 높이를 줄여** 키보드를 흉내 냈다. 8줄 넘게 입력하는 동안 칸 아래 끝 348px < 보이는 영역 360px였다.
  실제 가상 키보드는 레이아웃 뷰포트를 줄이지 않고 visualViewport만 줄이는 등 동작이 달라, 이 결과로 실기기 동작을 보장할 수 없다.
- **iOS Safari에서 특히 확인할 것**
  - 키보드가 열릴 때 `visualViewport` `resize`가 늦게 오거나, 대신 `scroll`만 오는 경우가 있다(현재는 `resize`만 듣는다).
  - 포커스 때 Safari가 페이지 전체를 위로 밀어 올리는 자체 스크롤과 우리 스크롤이 겹쳐 두 번 움직일 수 있다.
  - 하단 버튼 — 요청 작성은 입력 중 하단 고정(`sticky`)을 풀지만, 워크스페이스 카드는 이전·다음 버튼이 카드 아래에 붙어 있고
    본문만 카드 안에서 스크롤돼 키보드가 올라오면 칸이 보일 영역이 더 좁다(칸 아래 끝 맞춤은 본문 스크롤 영역 기준으로 동작).
  - 주소창이 접히고 펴지면서 `visualViewport.height`가 바뀌는 동안 칸이 덜컹거리지 않는지.
- **확인 방법**: iPhone Safari·Android Chrome 실기기에서 요청 작성 "꼭 담아야 할 내용"과 워크스페이스 ★ 여러 줄 칸에 10줄 넘게 입력 → 입력 중인 줄이 키보드 위에 계속 보이는지.

## 3. 여러 줄 칸 글자 수 — 서버 쪽 길이 제한 미확인 (2026-10-16)

- **현재**: 여러 줄 칸(요청 작성 "꼭 담아야 할 내용", 워크스페이스 ★ 여러 줄 칸·◆ 긴 직접 입력)은 프런트 글자 수 제한·카운터가 **없다**
  (같은 날 1,000자 상한·카운터·경고색을 넣었다가 제거). 짧은 값(★ 한 줄 칸)만 `requestCards.ts` `TEXT_LIMITS.short` 40자.
- **이 저장소에서 확인할 수 없는 이유**: 이 저장소는 프런트 목업이다. 워크스페이스 "생성하기"(`App.tsx` `handleGenerate`)는 `setGenerated(true)`만 하고
  요청문을 어디에도 보내지 않는다. API 호출·서버 검증 코드가 없다.
- **봐야 할 곳**(실서비스 코드)
  1. 요청문을 받는 API의 요청 본문 검증 — 프롬프트·메시지 필드의 최대 길이(스키마 `max_length`, 검증 미들웨어, DB 컬럼 길이).
  2. 생성 툴(카드뉴스 `slide_count`를 검증했던 generate 툴 쪽)의 입력 인자 — 내용 텍스트를 받는 인자의 길이 제한·잘라내기(조용히 자르는지).
  3. LLM 호출 직전 프롬프트 조립부 — 전체 토큰 상한과, 넘을 때 앞/뒤를 자르는지.
- **한 칸이 아니라 합계로 봐야 한다**: 프런트는 칸 값을 따로 보내지 않고 한 덩어리 요청문으로 합친다
  (`RequestHelpScreen.tsx` `buildRequestText` = 작업·템플릿·주제·참고 자료·형식 값, 이어서 `RequestCardsPanel.tsx` `buildResult` = 카드 답 — 꼭 담을 내용은 ★ 카드에 채워져 여기 들어간다).
- **서버에 제한이 있다면**: 프런트에 제한이 없으므로 긴 글이 서버에서 잘리거나 거절될 수 있다. 그때는 서버 값에 맞춰 다시 상한을 둘지(안내 방식 포함) 정해야 한다.

## 4. 레이어 분리 에디터 — 모바일(375px)에서 상단바 넘침 (2026-10-16)

- 홈 아이콘 줄 "레이어 분리"는 `TabletMiniEditor`를 전체 화면으로 바로 연다. 1280px에선 정상.
- 375px에선 에디터 상단바(실행 취소·확대/축소·크레딧·검색·공유·저장·기록·다운로드·닫기)가 화면 폭을 넘어 **닫기 버튼이 화면 밖**에 있다.
  오른쪽 속성 패널도 접힌 채 일부만 보인다. 이 에디터는 태블릿 이상 기준으로 만들어진 것이라 기존 진입로(`?textsplit=1`, 워크스페이스 이미지 결과)도 같다.
- 처리 안 함: 에디터 자체 반응형은 이번 범위(홈 진입 구조) 밖. 모바일에서 막을지(안내만 띄우기), 상단바를 줄일지 정해야 한다.
